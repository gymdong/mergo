# 머고 시나리오 확장·경험 기반 학습 논의 정리

> **용도:** Claude Code가 사용자와의 설계 대화를 이어받기 위한 문서. 2026-10-30, `fix/post-ai-merge`의 `ae86d7a` 기준. **이 문서는 제안과 논의 결과이며 구현 완료나 MVP 스펙 변경을 뜻하지 않는다.** 기존 확정 스펙은 [`mergo-mvp-spec.md`](./mergo-mvp-spec.md)다.

## 1. 대화에서 합의한 방향

1. 기존 시나리오(S1·S2·S3·S4·S6·S11 등)만으로 실제 어르신의 다양한 막힘을 다루기 어렵다. 새 행동을 많이 자동화하기보다 **상황을 더 잘 구분하고, 불확실하거나 위험하면 묻거나 멈추는 것**을 우선한다.
2. 현재 머고는 **규칙 기반 감지·복구 + 제한된 LLM 화면 조작 에이전트**다. 이를 범용·완전 자율 에이전트나 스스로 학습하는 앱으로 설명하면 과장이다. 다만 안전 규칙에 `if`문이 있다는 사실은 문제가 아니다.
3. 도와줘 발화에서 키워드 후보가 없거나 여러 개면 **이미 LLM API를 호출한다**. 그러나 LLM 추론은 그 자체로 사용 경험을 학습해 다음 판단을 갱신하는 것이 아니다.
4. 제안하는 다음 단계는 **기기 내 작은 적응형 판단 모델**이다. 기존 LLM은 낯선 발화를 해석하고 도움 후보를 만들며, 새 모델은 사용자 피드백과 검증 결과를 바탕으로 **언제 제안할지·어떤 후보를 먼저 제시할지**를 조정한다. 설치·결제·권한 승인 등 안전 경계와 허용 행동 목록은 학습 대상이 아니다.
5. 낯선 상황에 대해 LLM이 선택한 행동 중 **사용자가 승인하고 실제 결과가 검증된 사례**를 다음 유사 상황의 참고 자료로 사용할 수 있다. 이는 *경험 기반 적응/검색*이지 LLM 가중치의 재학습은 아니다. 작은 개인화 모델과 사례 검색은 별개의 기능이다.

## 3. 확장해 볼 어르신 시나리오

| 페르소나/상황 | 현재 방식의 위험 | 우선 대응 |
|---|---|---|
| 영상을 일부러 일시정지하거나 다른 영상을 고름 | 막힘으로 오인해 되돌릴 수 있음 | 자동 복구 금지, 실제 재생 상태와 사용자 의도를 구분 |
| “소리가 안 나”지만 음량은 정상 | `KeywordRules`가 바로 `set_volume` 후보로 분류 | 일시정지·외부 출력·영상 자체 무음 등 확인, 불명확하면 질문 |
| 영상이 작은 플레이어로 남거나 로딩 중 | 앱/영상 제목만으로 화면 상태를 구분하기 어려움 | 관측 가능한 신호가 검증되기 전에는 안내만 제공 |
| “아까 거”가 직전 앱과 직전 영상 모두를 뜻할 수 있음 | 잘못된 곳으로 이동할 수 있음 | 두 후보를 큰 버튼으로 제시하고 선택 전에는 조작하지 않음 |
| 설치·로그인·권한·결제 화면에서 “안 꺼져” | 안전한 닫기와 위험한 조작을 혼동할 수 있음 | 민감 화면은 조작 중단·설명, 안전한 닫기가 검증된 일반 팝업만 예외 |
| TTS를 못 듣거나 TV 소리가 “네”로 인식됨 | 무응답·타인 음성을 사용자 의도로 오해 | 무응답은 학습 라벨로 쓰지 않음; 음성만으로 화자를 인증한다고 가정하지 않음 |

시나리오를 추가할 때는 `상황 → 관측 신호 → 사용자 의도 후보 → 허용/금지 행동 → 성공 검증 → 정상 사용 반례` 형태로 테스트 가능한 카드로 기록한다. **오탐 0에 가까운 정상 사용 테스트**가 새 자동 제안 수보다 중요하다.

## 4. 제안하는 적응형 구조

```text
MergoService: 화면·기기 신호 수집
  → StuckDetector / KeywordRules / LLM: 허용된 도움 후보 생성
  → FeatureExtractor: 개인정보를 최소화한 상황 특징 생성
  → AdaptiveRanker: 후보의 유용성·성공 가능성 점수
  → PolicyGate: 제안 / 먼저 질문 / 아무것도 하지 않음 / 안전 중단
  → MergoController: 사용자 선택 후 레시피 실행·객관적 검증
  → FeedbackStore: 선택과 검증 결과 기록
  → OnlineUpdater: 다음 판단에 쓸 개인화 점수 갱신
```

- **처음에는 기존 규칙이 기본값이다.** 사용자 데이터가 적을 때 학습 모델의 추정을 신뢰해 기존 안전 경로를 뒤집지 않는다.
- `AdaptiveRanker`는 후보 **순서·제안 시점·질문 필요 여부**만 바꾼다. 새로운 레시피를 만들어 실행하거나 안전 규칙을 완화하지 않는다.
- 구현 후보는 상황별 보수적 통계 모델(수락·거절·검증 성공을 별도로 누적)부터 시작한다. 충분한 라벨과 평가 체계가 생기면 온라인 선형 모델 등으로 확장할 수 있다. **모델 종류·임계값은 아직 확정하지 않았다.**
- LLM을 호출하는 낯선 상황에는 `ExperienceStore`에서 검증된 유사 사례를 검색해 참고로 보낼 수 있다. LLM 결정은 여전히 `RecipeIds` 허용 목록, 확인 정책, `SafetyGuard`, 실행 후 검증을 통과해야 한다. 유사 사례 검색은 **모델 학습과 혼동하지 않는다.**
- 이 구조만으로 완전히 새로운 문제를 자동 발견·해결할 수는 없다. 관측 신호가 없거나 성공 기준을 정의할 수 없는 경우는 질문/안내/중단한다.

## 5. 학습 데이터와 라벨의 최소 계약

`FamilyLog`를 곧바로 학습 데이터로 쓰지 말고 별도의 `FeedbackStore`를 설계한다. **장기 저장 필요성 자체가 현 스펙의 10분 화면 기록 원칙과 충돌할 수 있으므로** 저장 형식·기간·삭제·동의를 먼저 제품 결정으로 확정해야 한다. 1차 후보는 화면 원문·스크린샷·음성 원본 없이 기기 안에 다음 정보만 보관하는 것이다.

- 상황 특징: 규칙 ID, 앱 종류, 재생 상태, 제목 변화 여부, 최근 사용자 동작 간격, 음량 0 여부, 연결/출력 상태의 `UNKNOWN` 포함 값 등.
- 결정: 후보 레시피, 규칙/LLM/학습 모델 출처, 제안 여부, 사용자가 고른 후보.
- 피드백을 **분리**: `YES`는 도움 필요 신호, `NO`는 그때 그 제안에 대한 거절, `NONE`은 미관측. `Verifier` 성공/실패는 레시피 효과 신호. 완료 확인의 명시적 `NO`는 잘못된 결과 신호다. 이 라벨을 하나의 “성공” 불리언으로 뭉치지 않는다.
- 학습 정책 버전과 되돌리기 수단. 사용자가 데이터를 삭제하면 개인화도 초기화한다.

**선행 수정:** 현재 `Recipe.run()`은 `Boolean`이고, `LlmScreenAgent`는 한 번 행동 후 LLM의 `done`이면 독립 검증 없이 성공으로 돌려줄 수 있다 (`agent/LlmScreenAgent.kt:22-70`). `SkipAd`는 기다리다 안내만 해도 `true`를 돌려준다 (`recipe/SimpleRecipes.kt:56-75`). `MergoController`는 완료 확인 무응답도 해결로 기록한다 (`core/MergoController.kt:202-235`). 이 상태에서 학습하면 잘못된 성공 라벨이 쌓이므로 `검증 성공 / 안내만 함 / 검증 불가 / 실패`를 구분하는 결과 계약과 테스트가 먼저다.

## 6. 권장 구현 순서와 검증

1. **계약·반례 고정:** `docs/`에 시나리오 카드와 정상 사용 반례를 추가하고 기존 테스트를 유지한다. `model/` 변경은 A/B 공동 계약으로 조정한다 (`work-split.md:7-15`).
2. **관측·검증:** 재생 상태 등 필요한 신호를 `BrainContext`에 추가하고, 객관적 복구 검증 및 결과형을 먼저 고친다. 관측 불가 값은 `UNKNOWN`으로 둔다.
3. **첫 학습 범위 하나만:** “아까 거”의 앱/영상 후보 선택을 기록하고, 다음 유사 상황에서 후보 **표시 순서만** 바꾼다. 선택 전 자동 실행은 하지 않는다. 이후 자동재생 제안 시점 개인화로 확장할 수 있다.
4. **평가:** 과거 이벤트 시퀀스 재생 → 학습 결과가 실제 판단에 영향을 주지 않는 *shadow mode* → 제한적 반영. 정상 사용에서 잘못 제안한 횟수, 후보 선택 정확도, 검증된 복구율, 위험 조작 0회를 비교하고 악화되면 즉시 기본 규칙으로 되돌린다.
5. **그다음 낯선 상황:** 검증된 사례 검색을 LLM 입력에 추가하되, 저장·검색의 개인정보 정책과 프롬프트 안전성 테스트를 별도 통과시킨다.

## 7. 감지 일반화와 자기 개선 범위 (2026-10-30 추가 논의)

### 7.1 범용 이상 신호는 기존 규칙을 대체하지 못한다

"오래 무입력·반복 탭·뒤로가기 반복" 같은 범용 신호로 R1~R4를 대체할 수 있는지 검토했다. 결론은 **불가**다.

| 사례 | 지금 잡는 근거 | 범용 신호로 |
|---|---|---|
| S1 자동재생 (R1) | 카운트다운 + 터치 없는 제목 변경 + 이전 영상 30초 이상 시청 + 10초 무동작 | 못 잡음. 10초 무동작은 정상 시청과 같다 |
| S3 홈 이탈 (R2) | 직전 재생 중 + 홈에서 20초 | 약함. 폰을 내려놓은 것과 구분 안 됨 |
| S2 오조작 (R3) | 사용자가 제목을 바꾼 뒤 30초 안에 뒤로가기 연타·홈 이탈 | 부분적. 뒤로가기 반복은 잡히지만 일반 이동과 섞여 오탐 증가 |
| S11 광고 (R4) | 건너뛰기 노드가 보이고 5초 무동작 | 못 잡음. 행동이 아니라 화면 상태 신호다 |
| S4·S6·S8 | 원래 발화로 시작 | 호출어 경로로 해결. 감지 문제 아님 |

어르신의 막힘은 대부분 **조용한 막힘**(멈춰서 기다림)이고, 무반응은 정상 사용과 겉보기가 같다. R1~R4는 시나리오별 분기라기보다 **"이 조용함이 막힘인 이유"를 직전 맥락으로 증명하는 장치**다. LLM에 화면을 보여줘도 사용자가 새 영상을 원했는지는 화면에 없으므로 같은 한계가 남는다.

### 7.2 감지는 '정상 상태·원인·반응' 틀로 일반화한다

```text
정상 상태(baseline)에서 벗어남
  × 원인: 사용자가 바꿈 / 시스템·앱이 바꿈(자동재생·광고·홈 이탈)
  × 반응: 무반응(조용한 막힘) / 혼란 행동(연타·뒤로가기)
```

R1은 시스템 변경+무반응, R3는 사용자 변경+혼란 행동, R4는 앱 삽입+무반응이다. 새 자동 제안 시나리오는 판단 로직을 새로 쓰지 않고 **이탈 종류와 원인을 보여주는 관측 신호**를 등록하는 방식으로 추가한다. 원인 증거가 없으면 자동 제안하지 않는다.

### 7.3 경로별 역할

1. **사용자 호출(호출어 → LLM):** 범용성의 주력. 감지가 필요 없으므로 규칙이 놓친 상황은 대부분 여기서 LLM·화면 에이전트로 흡수한다. 유예 듣기 폐지로 이 경로의 비중이 커졌다.
2. **자동 감지(규칙):** 페르소나 기반 시나리오 카드를 사전 지식으로 넣되, 관측 신호와 정상 사용 반례가 있는 것만 자동 제안 대상으로 한다. 신호가 없는 시나리오는 호출 경로의 프롬프트 예시·테스트 케이스로 쓴다. 시나리오 우선순위는 가상 페르소나만이 아니라 실제 어르신 관찰로 확인한다.
3. **범용 신호:** 보조. 잡혀도 실행하지 않고 "도와드릴까요?"만 띄운다.

### 7.4 호출이 곧 학습 라벨이다 — 승격 단계

사용자가 호출어로 도움을 요청한 순간은 **"규칙은 못 잡았지만 실제로 막혀 있었던 상황"**의 라벨이다. 이를 다음 단계로만 승격한다.

| 단계 | 조건 | 동작 |
|---|---|---|
| 1. 기록 | 호출 → LLM 해결 → **객관적 검증 성공** | 상황 특징 + 해결 절차를 `ExperienceStore`에 저장 |
| 2. 해결 재사용 | 비슷한 상황에서 다시 호출 | 저장된 절차를 LLM 없이 재실행하고 다시 검증. 실패(앱 UI 변경 등)하면 절차를 폐기하고 LLM 경로로 복귀 |
| 3. 먼저 묻기 | 같은 맥락 직후 호출이 반복됨 | 호출 전에 "지난번처럼 ○○ 해드릴까요?" 제안. 실행은 확인 후 |
| ✗ 자동 수정 | — | 확인 없이 알아서 고치는 단계는 두지 않는다 |

한 번의 사례는 우연일 수 있고, 저장된 상황 특징이 정상 사용과 구분되는지 앱이 스스로 확신할 수 없기 때문이다. 검증되지 않은 해결(LLM의 `done`만 있는 경우, 안내만 한 경우)은 1단계에 들어가지 않으므로 §5의 결과 계약이 선행 조건이다.

### 7.5 코드 수정 없이 개선되는 범위

| 앱이 스스로 조정 | 사람이 코드로 추가 |
|---|---|
| 제안 여부(계속 거절하면 줄임), 제안 시점, 후보 순서 | 새 관측 신호(미니플레이어·오디오 출력 등 지금 읽지 않는 정보) |
| 검증된 사례 검색으로 LLM 판단 보강 | 새 행동 종류(시스템 API·권한이 필요한 레시피) |
| 검증된 화면 조작 절차의 재사용 | 새 상황의 성공 기준 정의 |
| 반복 호출 맥락의 "먼저 묻기" 승격 | 안전 경계(학습 대상 아님) |

기기 한 대의 데이터는 적어 개인화가 느리다. 체감할 만한 개선은 동의를 받은 사례를 모아 **팀이 검토해 새 신호·레시피·시나리오 카드로 반영하는 루프**가 함께 있어야 한다.

**설명할 때의 표현:** "정해진 능력 범위 안에서는 사용자에게 맞춰 스스로 판단을 다듬고, 범위 밖의 막힘은 사용자 호출로 발견해 해결법을 기억하며, 능력 자체는 팀과 함께 넓힌다." "한 번 겪은 문제는 다음부터 알아서 고친다"는 과장이다.

## 8. 아직 결정하지 않은 것

- 학습 데이터 저장 동의, 보관 기간, 삭제 UI, 가족 리포트와의 구분.
- 개인화의 첫 대상이 후보 **순서만**인지, 제안 시점까지 포함할지.
- 실제 기기에서 재생 상태·미니플레이어·오디오 출력·민감 화면을 얼마나 안정적으로 관측할 수 있는지.
- 충분한 학습 사례 수와 허용 가능한 오탐 기준. 임의의 숫자를 먼저 고정하지 말고 기존 동작을 기준으로 검증한다.
- §7.4 승격 기준: "비슷한 상황"의 판정 방법, "먼저 묻기"로 승격할 반복 횟수, 저장 절차의 만료 조건.
- 여러 사용자 사례를 모으는 팀 검토 루프의 수집 동의·익명화 방식.

**Claude에게 필요한 핵심 해석:** 사용자는 “LLM API를 이미 부르는데 왜 학습이 아니냐”를 물었다. 답은 **현재 LLM 호출은 매번 추론할 뿐, 사용자 피드백으로 머고의 다음 판단 정책을 갱신하지 않기 때문**이다. 목표는 범용 LLM을 폰에서 재학습시키는 것이 아니라, 기존 LLM·규칙·안전장치 사이에 **검증된 피드백으로 갱신되는 작은 개인화 판단층**을 넣는 것이다.
