# 60대 페르소나 시나리오 카드와 복구 결과 4분류

> **용도:** [`adaptive-agent-learning-handoff.md`](./adaptive-agent-learning-handoff.md) §6-1(계약·반례 고정)과 §7.3(경로별 역할)의 첫 산출물. 2026-10-30, `fix/post-ai-merge` 기준. **가상 페르소나이며 실제 사용자 조사가 아니다.** 빈도·우선순위는 실제 어르신 관찰로 다시 확인한다. 구현 완료나 MVP 스펙 변경을 뜻하지 않는다.

## 1. 페르소나

| 인물 | 생활·주 사용 | 특성·머고와의 관계 | 주된 위험 |
|---|---|---|---|
| **박영숙 (67)** | 경북 거주, 혼자 산다. 낮에 거실에서 폰을 세워 두고 YouTube 트로트·건강 영상을 자동재생으로 이어 본다 | 노안으로 작은 글자를 못 읽음. 사투리가 강하고 말이 짧다("이거 왜 이래"). 막히면 그냥 기다린다 | 조용한 막힘(무반응)이 정상 시청과 구분되지 않음 |

| **한옥순 (69)** | 혼자 산다. 서울 사는 딸이 걱정해 머고를 설치해 줬다. YouTube 찬송가·옛날 드라마, 밤에 잠이 안 오면 폰을 본다 | 경도 인지 저하 초기. 방금 한 질문을 잊고 다시 묻는다. 앱 위치를 자주 잊고, 설정을 모르는 사이에 바꿔 놓는다 | 반복 호출이 학습을 왜곡, 영상을 틀어 둔 채 잠듦, 가족 기록의 민감 정보 |

## 2. 카드 형식

각 카드는 `상황 → 관측 신호 → 의도 후보 → 허용/금지 행동 → 성공 검증(결과 분류) → 정상 사용 반례 → 경로`로 쓴다.

- **경로:** `자동 감지`(원인을 보여주는 관측 신호와 반례가 있을 때만) / `호출`(사용자가 호출어로 말한 뒤 키워드·LLM이 판단) / `범위 밖`(조작하지 않고 안내·중단).
- **틀:** 자동 감지 카드는 handoff §7.2의 `이탈 × 원인 × 반응` 중 어디에 해당하는지 적는다.
- **관측 상태:** ✅ 지금 코드에서 읽음 / 🔶 아직 읽지 않거나 실기기 검증 필요. 🔶 신호에 기대는 행동은 신호가 확보되기 전까지 안내로 낮춘다.
- **결과 분류**는 §4의 `검증 성공 / 안내만 함 / 검증 불가 / 실패`를 쓴다.

## 3. 시나리오 카드

### 박영숙 (67)

**P1-1. 트로트 영상이 끝나고 자동재생으로 모르는 영상이 나옴** — 기존 S1·R1
- 관측: ✅ 카운트다운 노드, 터치 없는 제목 변경, 이전 영상 30초 이상 시청(정상 상태), 바뀐 뒤 10초 무동작
- 틀: 시스템 변경 × 무반응
- 의도 후보: 이전 영상으로 돌아가기 / 새 영상을 그냥 보기
- 허용: 확인 후 `restore_video`. 금지: 확인 없이 되돌리기
- 검증: 재생 화면 제목 == 정상 상태 제목 → 검증 성공. 제목을 읽지 못하면 검증 불가
- 반례: **재생목록·믹스를 일부러 틀어 둔 경우**에는 다음 곡이 의도다. 🔶 재생목록 표시 노드를 관측할 수 있는지 확인이 필요하다. 그 전까지는 제안의 "아니요"를 개인화 신호로 쓴다
- 경로: 자동 감지

**P1-2. 화면이 꺼졌다 켜졌더니 영상이 멈춰 있음, "이거 왜 안 나와"**
- 관측: 🔶 재생 상태(MediaSession `PLAYING`/`PAUSED`)는 아직 `BrainContext`에 없다. ✅ 볼륨·온라인 여부
- 의도 후보: 이어서 재생 / 인터넷 문제 / 소리 문제
- 허용: 재생 상태가 `PAUSED`로 관측되면 확인 후 화면 에이전트로 재생 버튼 탭. 금지: 재생 상태를 모를 때 아무 데나 탭
- 검증: 재생 상태 `PLAYING` → 검증 성공. 재생 상태를 못 읽으면 검증 불가
- 반례: **일부러 일시정지**(전화 받기·밥 먹기)한 경우다. 그래서 자동 감지는 하지 않는다
- 경로: 호출

**P1-3. "소리가 안 나" — 그런데 볼륨은 정상**
- 관측: ✅ 볼륨 > 0. 🔶 재생 상태, 영상 자체 무음 여부
- 의도 후보: 일시정지됨 / 영상 앞부분이 원래 조용함 / 출력 장치 문제(P2-1)
- 허용: 볼륨이 0이면 `set_volume`. 0이 아니면 `set_volume` 금지, 무엇이 문제인지 되묻거나 확인된 원인만 처리
- 검증: `set_volume`이면 볼륨 == 목표 > 0 → 검증 성공. 원인을 못 찾아 설명만 하면 안내만 함
- 반례: 볼륨을 일부러 낮춰 둔 경우. 그래서 S4는 자동 제안하지 않는다(스펙 §2)
- 경로: 호출. **수정함(2026-10-30):** 볼륨이 0이 아니고 줄어들지도 않았으면 `set_volume`을 고르지 않고 "소리는 켜져 있어요. 영상이 멈췄는지, 이어폰이 연결됐는지 봐 주세요."라고 안내한다. LLM이 골라도 막고, 레시피도 이미 목표 볼륨이면 `Guided`로 끝낸다(예전에는 아무것도 바꾸지 않고 "소리를 다시 켰어요"라고 했다)

**P1-4. 광고가 나왔는데 건너뛰기를 못 찾고 기다림** — 기존 S11·R4
- 관측: ✅ 건너뛰기 노드, 5초 무동작
- 틀: 앱 삽입 × 무반응
- 허용: 확인 후 건너뛰기 노드 클릭. 금지: 광고 본문·"자세히 알아보기" 클릭
- 검증: 클릭 후 건너뛰기 노드 사라짐 → 검증 성공. **건너뛸 수 없는 광고라 기다리다 안내만 하고 끝나면 안내만 함**(현재 코드는 `true`)
- 반례: 광고가 끝날 때까지 기다리는 데 익숙한 경우. "아니요, 볼게요"가 반복되면 제안을 줄인다
- 경로: 자동 감지

### 이정호 (63)

**P2-1. 블루투스 이어폰이 가방 속에서 연결돼 폰 스피커에서 소리가 안 남**
- 관측: 🔶 오디오 출력 장치(AudioManager 출력 장치 목록)는 아직 읽지 않는다. ✅ 볼륨
- 의도 후보: 폰 스피커로 듣고 싶음
- 허용: "이어폰으로 소리가 가고 있어요" 안내. 금지: 블루투스 설정 변경을 확인 없이 하기(현재 허용 행동 목록에 없음)
- 검증: 출력 장치 변경은 하지 않으므로 안내만 함
- 반례: 이어폰으로 듣고 있는 정상 상태. 자동 감지 대상이 아니다
- 경로: 호출. 출력 장치 신호를 추가하는 일은 사람이 코드로 해야 한다(handoff §7.5)

**P2-2. 영상이 화면 구석 작은 플레이어로 줄어듦, "영상이 작아졌어"**
- 관측: 🔶 미니플레이어 노드. 지금은 `VIDEO_PLAYER` 표시만 있어 전체 화면과 구분하지 못한다
- 의도 후보: 크게 다시 보기
- 허용: 확인 후 화면 에이전트로 미니플레이어 탭. 금지: 미니플레이어의 닫기(X) 탭
- 검증: 🔶 전체 화면 플레이어 신호가 확보되면 검증 성공/실패. 그 전에는 에이전트가 `done`이라 해도 검증 불가
- 반례: 목록을 둘러보려고 일부러 줄인 경우. 자동 감지하지 않는다
- 경로: 호출

**P2-3. 바둑 앱의 전면 광고가 안 닫힘, "이거 안 꺼져"** — S6 유형
- 관측: ✅ 화면 노드(에이전트가 읽음), ✅ 포그라운드 패키지
- 의도 후보: 광고만 닫고 바둑으로 돌아가기
- 허용: 확인 후 화면 에이전트가 닫기·뒤로 가기만. 금지: "설치"·"열기"·광고 본문 클릭(`SafetyGuard`), 스토어로 이동
- 검증: 광고 닫기 노드가 사라지고 포그라운드가 여전히 바둑 앱 → 검증 성공. 이런 목표 조건이 없으면 에이전트 `done`만으로는 검증 불가. 위험 노드 선택으로 중단 → 실패
- 반례: 광고 보상(무르기 1회 등)을 받으려고 일부러 광고를 보는 중
- 경로: 호출

**P2-4. 뉴스 영상을 보다 홈 버튼을 눌러 나왔고 20초 동안 그대로** — 기존 S3·R2
- 관측: ✅ 직전 재생 중, 런처 포그라운드, 20초 동안 다른 앱 안 열림
- 틀: 사용자 변경 × 무반응 (홈 이탈)
- 허용: 확인 후 `open_previous_app`
- 검증: 포그라운드 == YouTube → 검증 성공
- 반례: **일부러 나와서 시계·날씨 위젯을 보는 경우.** 오탐 가능성이 있으므로 제안만 하고, 거절이 반복되면 개인화로 줄인다
- 경로: 자동 감지

### 최미경 (68)

**P3-1. 손주 동요를 보다 추천 영상을 잘못 누르고 뒤로가기를 연타** — 기존 S2·R3
- 관측: ✅ 사용자 동작으로 제목 변경, 30초 안에 뒤로가기 3초 내 2회 또는 홈 이탈
- 틀: 사용자 변경 × 혼란 행동
- 허용: 확인 후 `restore_video`(시청 기록 우선)
- 검증: 재생 화면 제목 == 정상 상태 제목 → 검증 성공
- 반례: 다른 영상을 일부러 고른 뒤, 목록으로 돌아가려고 뒤로가기를 두 번 누른 경우. 그래서 확인 없이 실행하지 않는다
- 경로: 자동 감지

**P3-2. 카톡 사진을 보다 YouTube로 갔다가 "아까 거 보여 줘"**
- 관측: ✅ 직전 앱(카톡), ✅ 정상 상태 영상 제목
- 의도 후보: 카톡 사진(직전 앱) / 아까 보던 영상
- 허용: 두 후보를 큰 버튼으로 보여 주고 고른 것만 실행. 금지: 선택 전 조작
- 검증: 고른 쪽에 따라 포그라운드 == 카톡 또는 제목 일치 → 검증 성공
- 반례: 없음(호출 경로라 사용자가 먼저 원함). 다만 후보를 잘못 고르면 완료 확인 "아니요"로 잘못된 결과 라벨이 된다
- 경로: 호출. **handoff §6-3의 첫 학습 대상**(후보 표시 순서 개인화). 현재 `KeywordRules`는 화면 변화(diff)로 둘 중 하나만 고르므로 두 후보 표시는 새로 만들어야 한다

**P3-3. 잘못 눌러 Play 스토어 설치·결제·권한 화면이 뜸, "이거 뭐야 꺼 줘"**
- 관측: ✅ 포그라운드 패키지(스토어·결제·시스템 권한). 🔶 민감 화면 판별 목록
- 의도 후보: 원래 화면으로 돌아가기
- 허용: 조작하지 않고 "누르지 않으셔도 돼요. 왼쪽 아래 뒤로 버튼을 누르시면 돼요"라고 안내. 가족 알림을 제안한다. 금지: 설치·구매·허용·동의는 물론 이 화면 안의 어떤 탭도 자동으로 하지 않는다
- 검증: 조작하지 않으므로 안내만 함
- 반례: 가족이 시킨 앱을 직접 설치하는 중. 그래서 자동 감지로 끼어들지 않는다
- 경로: 범위 밖

**P3-4. 와이파이가 꺼져 "유튜브가 안 나와"** — 기존 S8
- 관측: ✅ 온라인 여부(`BrainContext.current.online`)
- 허용: 확인 후 `open_internet_panel`
- 검증: 10초 안에 `online=true` → 검증 성공 / 아니면 실패
- 반례: 데이터를 아끼려고 일부러 꺼 둔 경우. 자동 제안하지 않는다
- 경로: 호출. **현재 `MergoService`의 레시피 목록에 `open_internet_panel` 구현이 등록돼 있지 않아**, 이 후보가 골라지면 "인터넷을 다시 연결해 볼까요?"라고 말만 하고 아무것도 하지 않는다(§4.4, 스펙상 스트레치 항목)

### 정만석 (66)

**P4-1. 자동재생 제안이 떴지만 음성 안내를 못 듣고 말풍선도 못 봄** — R1 제안의 반응 문제
- 관측: ✅ 제안에 대한 무응답(`YesNo.NONE`). 🔶 보청기·청각 보조 설정 여부
- 의도 후보: 못 들음 / 그냥 보고 싶음 / 자리를 비움
- 허용: 말풍선 글자를 크게 하고 진동 등 소리 외 알림을 준다(🔶 설정 항목 필요). 금지: 무응답을 "아니요"와 같은 학습 라벨로 쓰기
- 검증: 실행하지 않았으므로 결과 분류 대상이 아니다
- 반례: 이 페르소나 자체가 다른 카드의 반례다. **지금 컨트롤러는 무응답을 거절과 똑같이 처리해**, 같은 대상에 다시 제안하지 않고 지금 상태를 정상 상태로 인정한다(`core/MergoController.kt:139-143`). 화면 동작으로는 합리적이지만 학습 라벨로는 구분해야 한다
- 경로: 자동 감지(기존 R1)의 반응 처리

**P4-2. 영상을 보다 전화를 받고 끊었더니 YouTube가 아니라 통화 기록 화면, "보던 거 어디 갔어"**
- 관측: ✅ 포그라운드 패키지 변화(YouTube → 전화 앱), ✅ 정상 상태 영상. 🔶 통화 중 여부(전화 상태)는 읽지 않는다
- 틀: 시스템 변경(수신 전화) × 무반응 — 단, 통화가 끝난 뒤에만
- 의도 후보: 영상으로 돌아가기 / 다른 사람에게 다시 전화하기
- 허용: 통화가 끝난 것이 확인된 뒤 확인 후 `open_previous_app`. 금지: **통화 중 어떤 말풍선·음성·조작도 하지 않는다**
- 검증: 포그라운드 == YouTube → 검증 성공
- 반례: 통화 직후 다른 곳에 전화를 거는 경우. 그래서 자동 제안 전에 통화 상태 신호(🔶)가 먼저 필요하다. 그 전까지는 호출로만 처리한다
- 경로: 호출. 통화 상태 신호가 확보되면 R2의 "홈" 조건을 "전화 앱"으로 넓힌 자동 감지 후보

**P4-3. "택배 주소 확인" 문자의 링크를 눌러 낯선 웹페이지가 뜸, "이거 뭐야"**
- 관측: ✅ 포그라운드가 브라우저, ✅ 화면 글자. 🔶 직전 앱이 문자 앱이었는지, 입력 칸(전화번호·카드번호) 존재
- 의도 후보: 무엇인지 알고 싶음 / 닫고 싶음
- 허용: 조작하지 않고 "모르는 문자의 링크예요. 아무것도 입력하지 마세요"라고 안내하고 가족 알림을 제안한다. 금지: 이 페이지의 어떤 입력·클릭도 자동으로 하지 않는다. 진위를 판정해 "안전해요"라고 말하지 않는다
- 검증: 조작하지 않으므로 안내만 함
- 반례: 진짜 택배 문자. 머고는 진위를 모르므로 어느 경우든 같은 안내를 한다
- 경로: 범위 밖

**P4-4. 주머니에서 비행기 모드가 켜져 "전화가 안 돼", "인터넷이 안 돼"**
- 관측: ✅ 온라인 여부. 🔶 비행기 모드 상태
- 의도 후보: 비행기 모드 끄기
- 허용: 확인 후 인터넷 패널 열기. 🔶 이 패널에 비행기 모드 토글이 있는지는 기기·버전별로 확인이 필요하다. 없으면 "화면 위를 내려서 비행기 모양을 누르세요"라고 안내한다
- 검증: 10초 안에 `online=true` → 검증 성공. 안내로 끝나면 안내만 함
- 반례: 일부러 비행기 모드를 켠 경우(병원·잠자기). 자동 제안하지 않는다
- 경로: 호출. 지금 `KeywordRules`는 오프라인일 때 "안 돼"가 들어간 말을 인터넷 패널 후보로 고르므로(`ai/KeywordRules.kt:61`) "전화가 안 돼"도 여기에 걸린다. 비행기 모드일 때는 맞지만, 상대가 안 받는 등 통화 자체의 문제와는 구분하지 못한다. 🔶 발화 테스트셋에 추가한다

### 한옥순 (69)

**P5-1. 5분 안에 "아까 그 드라마 어디 갔어"를 세 번 호출**
- 관측: ✅ 호출 시각·발화, ✅ 직전 레시피와 결과
- 의도 후보: 첫 호출의 해결을 잊음 / 실제로 다시 막힘
- 허용: 지금 화면이 이미 목표 상태면 아무것도 누르지 않고 "지금 보고 계신 게 그 드라마예요"라고 안내한다. 금지: 같은 레시피를 반복 실행해 화면을 흔들기
- 검증: 이미 목표 상태면 검증 성공 + 조작 없음, 안내로 끝나면 안내만 함
- 반례: **이 카드는 handoff §7.4 승격 단계의 반례다.** 짧은 시간의 반복 호출은 "같은 맥락에서 자주 막힌다"는 증거가 아니다. 승격 횟수를 셀 때 같은 상황의 연속 호출은 한 번으로 묶는다
- 경로: 호출

**P5-2. 홈 화면에서 YouTube 아이콘을 못 찾음, "유튜브 어딨어"**
- 관측: ✅ 런처 포그라운드, ✅ 발화
- 의도 후보: YouTube 열기
- 허용: 확인 후 YouTube 실행(`open_previous_app`과 같은 앱 실행 행동, 대상 패키지만 다름). 금지: 아이콘 위치를 옮기거나 홈 화면을 정리하기
- 검증: 포그라운드 == YouTube → 검증 성공
- 반례: 없음(호출 경로). 다만 "유튜브"가 아니라 "그 노래 나오는 거"라고 말하면 대상 앱이 모호하므로 후보를 보여 준다
- 경로: 호출. **구현함(2026-10-30):** `open_previous_app`에 `params.app`으로 [`KnownApps`](../app/src/main/java/app/mergo/model/Apps.kt) 허용 목록(유튜브·카카오톡·사진첩·카메라)의 앱만 연다. 앱 이름과 "어딨어·열어·켜 주세요" 같은 요청 말이 함께 있을 때만이고, "아까 보던 거"나 불평("이상해")이 섞이면 앱 열기로 보지 않는다. LLM이 패키지를 고르거나 목록에 없는 앱을 고르면 열지 않는다

**P5-3. 화면이 옆으로 누웠거나 글자가 갑자기 커짐, "화면이 이상해"**
- 관측: 🔶 화면 회전 고정 여부, 글꼴 크기·화면 배율 설정. 지금은 읽지 않는다
- 의도 후보: 원래대로 돌리기
- 허용: 원인이 관측되면 무엇이 바뀌었는지 설명하고 안내한다. 금지: 시스템 설정을 자동으로 바꾸기(허용 행동 목록에 없음, 알림창은 감지에서 제외된 `com.android.systemui`)
- 검증: 안내만 함
- 반례: 딸이 일부러 글자를 키워 준 경우. 그래서 "원래대로"의 기준을 정상 상태가 아니라 사용자에게 묻는다
- 경로: 호출. 설정 변경을 행동으로 넣으려면 새 신호와 레시피를 사람이 추가해야 한다(handoff §7.5)

**P5-4. 밤에 드라마를 틀어 둔 채 잠들어 자동재생이 계속됨**
- 관측: ✅ 자동재생 카운트다운, 터치 없는 제목 변경, 제안 무응답
- 틀: 시스템 변경 × 무반응 — R1 조건을 그대로 만족한다
- 의도 후보: 자고 있음(도움 불필요)
- 허용: 제안하지 않거나, 무응답이 이어지면 이후 제안을 멈춘다. 금지: 밤새 음성 안내로 깨우기
- 검증: 실행하지 않았으므로 결과 분류 대상이 아니다
- 반례: **R1의 정상 사용 반례.** 지금은 무응답이면 새 영상을 정상 상태로 인정하고 R1이 5분 쉰다(`detect/Cooldown.kt`). 그런데 무응답 때 새 영상을 정상 상태로 바로 인정하므로(`acceptCurrent`), 5분 휴식이 끝난 뒤의 다음 자동재생에서 R1 조건이 다시 성립한다. 대상 제목이 매번 달라 쿨다운에도 막히지 않아, 밤새 몇 분마다 음성 제안이 반복됐다(JVM 테스트로 재현: 자동재생 3번에 제안 3번). **수정함:** 자동 제안에 무응답이면 사용자 동작(터치 등)이나 직접 호출이 올 때까지 자동 제안을 멈춘다(`StuckDetector.pauseUntilUserAction`). 명시적 "아니요"는 기존처럼 같은 대상만 막고 규칙을 5분 쉰다
- 경로: 자동 감지(기존 R1)의 반례. 첫 제안 한 번은 남는다(깨어 있는 정상 R1과 구분할 수 없음). 그것까지 줄이려면 화면 꺼짐·야간 시간대 신호가 필요하다

### 공통 반례

- **TV 소리가 "네"로 들림(최미경):** 음성만으로 화자를 구분하지 못한다. 위험하거나 되돌리기 어려운 행동의 확인은 버튼을 우선하고, 음성 "네"만으로 받은 확인은 학습 라벨에서 따로 표시한다.
- **무응답(정만석·한옥순):** 못 들었는지, 괜찮다는 뜻인지, 자거나 자리를 비웠는지 모른다. 무응답은 어떤 학습 라벨로도 쓰지 않는다(handoff §5). 화면 동작에서 거절처럼 쉬는 것은 괜찮다.
- **짧은 시간의 반복 호출(한옥순):** 승격 단계의 반복 횟수로 세지 않는다.
- **가족 기록의 민감 정보(한옥순):** 반복 질문이나 밤 시간 사용 같은 기록은 인지 상태를 드러낼 수 있다. 가족 리포트에 무엇을 보여 줄지는 handoff §8의 동의·보관 결정과 함께 정한다.

## 4. 복구 결과 4분류

### 4.1 정의

| 분류 | 뜻 | 판정 기준 |
|---|---|---|
| **검증 성공** | 머고가 행동했고, 목표 상태가 실제로 됐다 | 행동 **이후** 독립 관측값(제목·볼륨·포그라운드 패키지·노드 사라짐·온라인 여부)이 목표 조건과 일치한다. LLM의 `done`, `click()`의 반환값, 사용자의 "네"는 독립 관측이 아니다 |
| **안내만 함** | 일부러 조작하지 않고 말·화면 안내로 끝냈다. 이것이 정해진 결말이다 | 레시피나 정책이 "여기서는 안내가 정답"이라고 정한 경로로 끝났다. 예: 건너뛸 수 없는 광고, 민감 화면, 허용 목록에 없는 설정(블루투스) |
| **검증 불가** | 행동은 했지만 목표 상태를 확인할 수단이 없다 | 목표 조건이 정의돼 있지 않거나(에이전트 목표가 자유 문장), 관측값을 읽지 못했다(제목 `null`, 재생 상태 미지원). **"읽었더니 달랐다"가 아니라 "읽지 못했다"** |
| **실패** | 시도했는데 목표에 닿지 못했거나 중간에 멈췄다 | 관측값이 목표와 다르다. 또는 전제 조건 없음(정상 상태 제목 없음), 레시피 미등록, `SafetyGuard` 중단, 단계·시간 초과, LLM `fail`, 예외 |

### 4.2 판정 순서

```text
1. 조작 없이 정해진 안내로 끝났나?            → 안내만 함
2. 시작 못 함 / 중단 / 초과 / 예외였나?         → 실패 (사유 코드 기록)
3. 이 목표에 독립 검증 조건이 있고 값을 읽었나?
     아니요                                    → 검증 불가
     예, 일치                                  → 검증 성공
     예, 불일치                                → 실패 (목표 미도달)
```

- 이미 목표 상태라 아무것도 누르지 않은 경우(예: `RestoreVideo`에서 이미 그 영상을 보고 있음)는 **검증 성공이되 `조작 없음`으로 표시한다.** 제안 자체가 불필요했다는(오탐 가능성) 신호이기 때문이다.
- 사용자의 완료 확인("이 화면이 맞나요?")은 위 분류를 바꾸지 않는 **별도 필드**다. 검증 성공인데 명시적으로 "아니요"라고 하면 *잘못된 결과*(목표 자체를 잘못 골랐음) 라벨이 붙는다. 검증 불가인데 "예"라고 하면 *사용자 확인*으로만 남기고, 검증 성공으로 올리지 않는다.

### 4.3 분류별 머고의 반응과 학습 사용

| 분류 | 사용자에게 | 가족 기록 | 경험 저장(handoff §7.4) |
|---|---|---|---|
| 검증 성공 | "다 됐어요" + 완료 확인 | 해결 | 저장 대상. 단 완료 확인 "아니요"면 제외 |
| 안내만 함 | 안내 문장만. "해결하지 못했어요"라고 하지 않음 | 안내함(해결과 구분) | 저장하지 않음. 레시피 성공률에 넣지 않음 |
| 검증 불가 | "제대로 됐는지 봐 주세요" + 완료 확인 **필수** | 미확인. 무응답을 해결로 기록하지 않음 | 저장하지 않음. 같은 목표가 자주 나오면 검증 조건을 사람이 추가할 후보 |
| 실패 | "해결하지 못했어요" + 가족 알림 질문 | 미해결 + 사유 | 저장하지 않음. 실패 사유는 레시피 개선 자료 |

### 4.4 코드 반영 (2026-10-30)

`Recipe.run()`이 `Boolean` 대신 `RecipeOutcome`을 돌려준다(`model/Recipes.kt`). 각 위치는 다음과 같이 분류한다.

| 위치 | 예전 | 지금 |
|---|---|---|
| `SkipAd` — 10초 기다려도 버튼 없음 | `true`(가족 알림 질문을 피하려는 거짓 성공) | `Guided`. 가족 알림을 묻지 않고, 리포트에 "안내함"으로 보인다 |
| `SkipAd` — 클릭 후 버튼이 사라지지 않음 | `false` | `Failed(NOT_REACHED)` |
| `SkipAd` — 클릭 후 화면 노드가 비어 옴(창 전환 중) | `true`(빈 화면을 '버튼 사라짐'으로 읽음) | `Unverifiable` |

| `RestoreVideo` — 조작 뒤 제목을 끝내 읽지 못함 | `false` | `Unverifiable`. 검증 함수가 `null`(읽지 못함)을 돌려줄 수 있다(`Verifier.waitFor`) |
| `OpenPreviousApp` — 열 앱도 정상 상태도 없음 | `false` | `Failed(PRECONDITION)` |
| `StepChain` — 여러 방법을 차례로 시도 | 하나라도 검증되면 `true` | 하나라도 검증되면 `Verified`, 아니면 **마지막으로 실행한 방법**의 확인 결과를 따른다(못 읽음 → `Unverifiable`, 달랐음 → `Failed`) |
| 등록되지 않은 레시피 / 실행 중 예외 | `false` | `Failed(NO_RECIPE)` / `Failed(ERROR)` |
| `MergoController.execute()` | 성공 + 완료 확인 무응답 = 해결 | `Verified`만 무응답을 해결로 본다. `Verified`인데 사용자가 "아니요"면 `verified_rejected`로 남긴다. `Unverifiable`은 "제대로 됐는지 봐 주세요" 뒤 "예"일 때만 해결, 무응답은 미확인, "아니요"는 가족 알림 질문. 확인 없이 실행 모드에서는 묻지 않고 미확인으로 남긴다 |

`FamilyLog.Entry.outcome`에 `verified`·`verified_noop`·`verified_rejected`·`guided`·`unverifiable`·`failed:사유`를 남긴다. 나중에 학습 라벨로 쓸 때 해결/안내/미확인/실패를 구분하기 위해서다. 예전 기록은 빈 값이다.

**아직 남은 것**
- `ScreenAgent.achieve()`는 여전히 `Boolean`(B 소유 `model/Screen.kt`)이라 안전 중단·단계 초과·LLM 포기를 `AGENT_GAVE_UP` 하나로 묶는다. 사유를 나누려면 이 계약을 바꿔야 한다.
- 에이전트 목표별 검증 조건(예: "광고 닫기" → 닫기 노드가 사라지고 같은 앱 유지)이 생기면 그 목표는 `Unverifiable` 대신 `Verified`/`Failed`로 바뀐다.
- `open_internet_panel`은 레시피 목록에 없다. 도와줘 경로에서는 `MergoController.onHelp`가 등록되지 않은 레시피를 되묻기처럼 처리해, Brain의 안내 문장("인터넷을 다시 연결해 볼까요?")만 말하고 아무것도 하지 않는다. 연결 누락인지 의도된 보류인지 정해야 한다.
